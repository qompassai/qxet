# qxet v0.1 build — observations (2026-10-17 night session)

- Built DESIGN.md v0.1 as a greenfield workspace (`crates/qxet-core`,
  `crates/qxet-cli`) rather than restoring the missing upstream
  workspace crates the fragments reference. The fragments pin a
  HuggingFace-xet restoration surface; DESIGN.md's v0.1 is a local
  CAS + CLI, and `hf_xet`'s shape is explicitly a v0.2 redo.
  Fragments kept, workspace-`exclude`d, README documents why.
- FastCDC parity is pinned by known-answer tests adopted from the
  reference implementation's published suite (`fastcdc` crate v5.0.0,
  v2020 module): all-zeros cut at maximum, odd-tail lengths, mask
  selection incl. the rounded-log2 bucket rule. GEAR table values
  were cross-checked two independent ways (published table vs the
  MD5 generation recipe from the C reference).
- Judgment calls where DESIGN.md was silent (all documented in code
  and README): `gc` is dry-run unless `--apply` is passed ("default-
  safe" read literally); the content ID printed by `put` is the
  manifest hash (the only ID `get` can resolve); duplicate `put`
  idempotence is achieved by scanning for an identical manifest
  because manifests carry a creation timestamp.
- Bug the tests caught: `Store::discover` walked `Path::parent()` of
  a relative `"."` start, which never ascends the real hierarchy —
  store discovery from a subdirectory failed. Fixed by absolutizing
  the start path first. Worth remembering for any path-walking code.
- `put` does not rehash chunks that already exist with the right
  size; integrity is enforced on read (`get`/`verify`) per the
  design's verify-on-read stance. A wrong-size file under a chunk
  hash is replaced on `put` (its name is its hash, so its correct
  content is known).
